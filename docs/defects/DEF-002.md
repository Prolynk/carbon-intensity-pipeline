# DEF-002 — Source revises forecast values, so measured accuracy depends on fetch time

| Field | Value |
|---|---|
| **ID** | DEF-002 |
| **Title** | Forecast values are revised after first publication, making `Mean Absolute Forecast Error` dependent on when the data was fetched |
| **Status** | **Open — accepted as a known limitation, measurement method documented** |
| **Type** | Methodology / data interpretation |
| **Severity** | Medium |
| **Priority** | Low |
| **Raised** | 7 Nov 2026 |
| **Raised by** | Observed while verifying the DEF-001 fix |
| **Component** | `Mean Absolute Forecast Error` and related DAX measures; `fact_intensity.forecast` |

---

## Summary

Re-fetching a window that had already been loaded showed that the source **changes
the forecast value it publishes for a period**. Of the 288 periods in the re-fetched
chunk, 5 came back with a different forecast from the one stored two days earlier —
all 5 revised upward, by between 5 and 23 gCO₂/kWh.

This means the published forecast is not a single fixed number per period. It is
refined as the period approaches. Any statement about forecast accuracy is therefore
a statement about a forecast *captured at a particular lead time*, and the project's
headline accuracy figure needs that caveat attached.

## Severity and priority

**Severity: medium.** It does not corrupt any stored value, and no metric is wrong.
But it undermines how a headline number should be *read*: "the forecast is accurate
to 12 gCO₂/kWh" is only meaningful alongside how far ahead that forecast was made.
Measuring against a late-revised forecast flatters the forecast, because a forecast
revised an hour before the period is an easier prediction than one made a day ahead.

**Priority: low.** No fix is needed for the current deliverable. The project does
not claim to measure forecast skill at a stated lead time, and the effect on the
reported figure is tiny at the current volume. It is recorded so the claim is not
overstated, and so anyone extending the project knows the trap is there.

## Environment

| | |
|---|---|
| First load | 5 Nov 2026, 21:41 UTC, run `cd0b2df18ad8` |
| Re-fetch | 7 Nov 2026, 13:33 UTC, 48-hour backfill |
| Endpoint | `GET /intensity/2026-10-31T00:00Z/2026-11-06T00:00Z` |
| Periods in the re-fetched chunk | 288 |

## Steps to reproduce

1. Load a window ending at the present moment.
2. Keep a copy of the database.
3. Two days later, re-run with `--backfill-hours 48`.
4. Compare `forecast` per `period_start_utc` across the two copies.

```sql
SELECT b.period_start_utc, b.forecast AS before, a.forecast AS after,
       a.forecast - b.forecast AS delta
FROM   before.fact_intensity b
JOIN   main.fact_intensity   a USING (period_start_utc)
WHERE  b.forecast <> a.forecast;
```

## Expected result

The forecast published for a given settlement period is fixed once published, so
re-fetching the same period returns the same forecast.

## Actual result

5 of 288 re-fetched periods returned a revised forecast.

## Evidence

```
period_start_utc       forecast_before  forecast_after  delta  settled_actual
2026-11-05T21:30:00Z             203.0           208.0     +5             214
2026-11-05T22:00:00Z             203.0           213.0    +10             213
2026-11-05T22:30:00Z             199.0           213.0    +14             220
2026-11-05T23:00:00Z             196.0           215.0    +19             222
2026-11-05T23:30:00Z             197.0           220.0    +23             223
```

Range +5 to +23, mean **+14.2 gCO₂/kWh**. Every revision moved the forecast toward
the eventual actual, and the size of the revision grows with how far ahead the
original forecast was made.

All 5 revised periods were **unsettled at first fetch** — they are 5 of the 6 from
DEF-001. The 283 periods in the chunk that had already settled came back with
**identical forecasts**. So the pattern is: a period's forecast is refined while it
is still in the future, and fixed once it settles.

### Related observation: settled actuals are also refined

The same comparison showed **28 periods whose already-settled actual changed**,
all within the final 24 hours of the window, by between **−2 and +2 gCO₂/kWh**
(mean +0.07, mean absolute 1.14). Nothing older than 24 hours moved.

```
2026-11-04T22:30:00Z  actual 146 → 144   (−2)
2026-11-05T06:00:00Z  actual 164 → 166   (+2)
2026-11-05T04:30:00Z  actual 135 → 137   (+2)
...
```

This is small-scale settlement refinement rather than revision, and it supports the
48-hour backfill window chosen for DEF-001: a shorter window would miss it.

## Impact

| Affected | How |
|---|---|
| `Mean Absolute Forecast Error` | Moved from 12.006 to 11.997 after the backfill — negligible at 5 of 4,320 rows, but the direction is systematic |
| `Forecast Within 20 %` | Unchanged at 84.3% |
| `Avg Forecast Intensity` | 116.05 → 116.18 |
| The claim "the forecast is accurate to 12 gCO₂/kWh" | Needs the caveat that lead time is mixed and unstated |
| Reproducibility | Two people loading the same window on different days get slightly different accuracy figures |

The practical risk is not today's number. It is that a future run with a longer
backfill window would quietly re-measure accuracy against better forecasts and
report an improvement that is an artefact of the method, not a real change.

## Likely cause

**Hypothesis.** The forecast is produced by a model that is re-run as new inputs
arrive, most likely updated wind and demand data, and the API serves the latest
forecast for a period rather than an immutable first publication. The behaviour is
consistent with that: revisions only affect future periods, they move toward the
actual, and they grow with lead time.

Not confirmed against the API's documentation, and recorded as a hypothesis. It is
**not a fault** — serving the best current forecast is reasonable. The issue is on
our side, in how accuracy is measured and described.

## Resolution

**Accepted as a known limitation.** Three actions taken:

1. The raw responses in `data/raw/` are retained as the source of record, and
   reconciliation tests (DQ-21 to DQ-25) compare the warehouse against *those saved
   files* rather than against whatever the API returns today. Without this, every
   reconciliation test would fail after a backfill.
2. `docs/test_plan.md` limitation 4 records the behaviour.
3. The `README` and the manager note describe accuracy as measured at mixed lead
   times, and do not claim a stated-lead-time forecast skill.

**Not fixed**, and deliberately so. Capturing forecast-at-fixed-lead-time would mean
storing every published revision with the time it was seen — a slowly changing
dimension on the fact table. That is the right design if the question becomes "how
good is the day-ahead forecast", and it is out of scope for the question this
project actually asks.

## Recommended next step if the project continues

Add `forecast_captured_at_utc` to `fact_intensity`, keep the first forecast seen for
each period as well as the latest, and report accuracy at a stated lead time. That
turns this limitation into the more interesting finding: how much the forecast
improves as the period approaches.
