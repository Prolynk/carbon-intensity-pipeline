# DEF-003 — Source duplicates are absorbed silently, so no test can see them

| Field | Value |
|---|---|
| **ID** | DEF-003 |
| **Title** | `transform.py` de-duplicates before validation, so a genuine source duplicate is invisible to every downstream check |
| **Status** | **Open — accepted, mitigation in place** |
| **Type** | Test coverage gap |
| **Severity** | Low |
| **Priority** | Low |
| **Raised** | 7 Nov 2026 |
| **Raised by** | Defect-fixture run — planted defect D1 was not caught by the test written for it |
| **Component** | `src/transform.py`, `src/validate.py` check `no_duplicate_periods`, test DQ-07 |

---

## Summary

A duplicate period was planted in the defect fixture to prove DQ-07
(`test_no_duplicate_period_starts`) could catch it. **DQ-07 passed.** The duplicate
was removed by `transform.py` before the data reached the database, so the test had
nothing to find.

The duplicate was still caught, by DQ-01 (row count), which is why the defect run
reports 7 of 7. But it was caught by accident rather than by the test designed for
it, and that is worth recording rather than glossing over.

## Severity and priority

**Severity: low.** The de-duplication is deliberate and correct for its purpose.
The pipeline fetches 90 days in 7 chunks and the API returns the settlement period
containing `from`, so neighbouring chunks genuinely overlap by one period. Removing
those is right. No incorrect data reaches the warehouse.

**Priority: low.** The scenario where this matters — the source returning the same
period twice *within a single response*, with different values — has not been
observed and may not be possible. The risk is theoretical.

## Steps to reproduce

```bash
python scripts/verify_defect_detection.py
```

Defect D1 plants a duplicate of the `2026-09-22T05:00Z` record in
`tests/fixtures/sample_with_defects.json`. Expected: DQ-07 fails. Actual: DQ-07
passes and DQ-01 fails instead.

## Expected result

A duplicate period in the source causes the check written for duplicates to fail,
and the run stops with a message naming the duplicated timestamp.

## Actual result

`transform.py` drops it:

```
transform  | dropped 1 duplicate period(s) from overlapping chunk seams
```

The message is logged at INFO and the run continues. `validate.py`'s
`no_duplicate_periods` check then runs on the already-de-duplicated frame and
reports `[PASS] no duplicate period starts`, which is true but misleading —
it means "there are none now", not "there were none".

By the time DQ-07 queries the database there is nothing to find. The only signal
is a row count one lower than expected, which DQ-01 catches but attributes to a
missing period rather than a removed duplicate.

## Evidence

From `docs/defect_detection_report.md`:

| ID | Planted defect | Caught | Tripped |
|---|---|---|---|
| D1 | duplicate_period | yes | `test_row_count_equals_days_times_48` |

Not `test_no_duplicate_period_starts`, which is the test the defect was written for.

## Impact

| Affected | How |
|---|---|
| Warehouse data | None. The de-duplication keeps the first record and is correct for chunk seams |
| DQ-07 | Can only ever pass. It is a regression guard against the de-duplication being removed, not a detector |
| `validate.py` `no_duplicate_periods` | Same — structurally cannot fail |
| Diagnosis | A duplicate and a missing period produce the same symptom, a row count one short, so the cause is ambiguous from the test output alone |

## Likely cause

Ordering. `transform.py` de-duplicates as part of flattening, because the seam
overlap is an expected property of chunked fetching. Validation runs after
transformation. Anything transformation repairs is therefore invisible to
validation by construction.

This is a general shape worth naming: **a cleaning step upstream of a checking step
hides exactly the defects it cleans.** The same would be true of any silent coercion
or fill.

## Resolution

**Accepted.** The de-duplication is correct and will stay. Mitigations:

1. The behaviour is recorded here, in `docs/test_plan.md` limitation 6, and in
   `tests/fixtures/planted_defects.json`, where D1 carries a note explaining why it
   is nominated against DQ-01 rather than DQ-07.
2. DQ-07 is retained as a **regression guard**. If the de-duplication were ever
   removed or moved, DQ-07 becomes a live detector again and the project should not
   lose it in the meantime.
3. `transform.py` already logs the count it dropped, so the information exists in
   `logs/pipeline.log` even though no assertion reads it.

## Recommended fix if this becomes worth doing

Make the de-duplication report rather than only log. Have `transform.transform`
return the dropped count alongside the frame, record it in the `pipeline_runs`
table, and add a test asserting it equals the expected seam count — 6 for a 7-chunk
fetch. Any duplicate beyond the predicted seams would then fail a test rather than
disappear into a log line.

That is roughly an hour of work and would convert this from an accepted gap to a
closed one. It is not done because the risk it guards against has not been observed.
