# DEF-001 — Six periods loaded with no settled actual

| Field | Value |
|---|---|
| **ID** | DEF-001 |
| **Title** | Six of 4,320 periods loaded with a forecast but no settled actual |
| **Status** | **Closed — fixed** (7 Nov 2026) |
| **Type** | Data availability |
| **Severity** | Low |
| **Priority** | Medium |
| **Raised** | 5 Nov 2026 |
| **Raised by** | `validate.py` check `missing_actuals`, on the pipeline run of 5 Nov 2026 |
| **Component** | `src/extract.py` (caching), `fact_intensity.actual` |
| **Fixed in** | 48-hour backfill, `extract.py` `backfill_hours` parameter |

---

## Summary

A 90-day load on 5 November 2026 wrote 4,320 half-hourly periods, of which **6 had
a forecast but no actual**. All six were the last six periods of the window, a
contiguous block covering 21:00–23:30 UTC on 5 November, loaded at 21:41 UTC the
same day.

## Severity and priority

**Severity: low.** It affects 6 of 4,320 periods, or 0.14%. The forecast is present
for all six, so no period is entirely missing. The nulls sit at the very end of the
window, so no historical analysis is affected. Nulls were stored as NULL rather than
imputed, so no metric was silently corrupted — averages simply exclude them.

**Priority: medium**, higher than the severity alone would suggest. The pipeline
caches raw responses and re-runs from the cache, so without a fix those six nulls
would have stayed null permanently, and every subsequent run would inherit them.
The defect does not get worse, but left alone it never heals either.

## Environment

| | |
|---|---|
| Date loaded | 5 November 2026, 21:41 UTC |
| Run ID | `cd0b2df18ad8` |
| Window requested | 2026-08-08T00:00Z to 2026-11-06T00:00Z (90 days, half-open) |

## Steps to reproduce

```bash
python src/run_pipeline.py --start 2026-08-08 --end 2026-11-06 --backfill-hours 0
```

Then:

```sql
SELECT period_start_utc, forecast, actual, intensity_index
FROM fact_intensity
WHERE actual IS NULL
ORDER BY period_start_utc;
```

Reproduces whenever the requested window ends at or near the present moment.

## Expected result

Every loaded period carries both a forecast and a settled actual, so that
`Mean Absolute Forecast Error` can be computed for all 4,320 periods.

## Actual result

6 periods carried a forecast and `NULL` in `actual`. The in-pipeline check
`missing_actuals` reported:

```
[WARN] missing_actuals: 6 period(s) (0.14%) have no actual yet
       -- expected near the end of the window
```

## Evidence

Query output at the time of the defect:

```
period_start_utc       forecast  actual  intensity_index
2026-11-05T21:00:00Z      205.0    NULL  high
2026-11-05T21:30:00Z      203.0    NULL  high
2026-11-05T22:00:00Z      203.0    NULL  high
2026-11-05T22:30:00Z      199.0    NULL  high
2026-11-05T23:00:00Z      196.0    NULL  high
2026-11-05T23:30:00Z      197.0    NULL  high
```

All six are consecutive and sit at the end of the window. The run completed at
21:41 UTC, so the earliest null is the period that was still in progress and the
rest had not yet occurred.

## Likely cause

**Hypothesis, now confirmed.** The source publishes a forecast for a period
immediately but the settled actual only after the period has passed and been
settled. The six nulls were periods at or beyond the moment of the run.

Confirmed on 7 November 2026 by re-requesting the same range:

```bash
curl "https://api.carbonintensity.org.uk/intensity/2026-11-05T21:00Z/2026-11-06T00:00Z"
```

All six periods now return a settled actual. Observed settlement lag is roughly
one to three hours. This is normal publication behaviour, **not a fault in the
API**, and is documented here as a data availability issue on our side: the
pipeline captured a snapshot before the data was complete and had no mechanism to
go back for it.

## Impact

| Affected | How |
|---|---|
| `Mean Absolute Forecast Error` | Computed over 4,314 periods instead of 4,320 |
| `Avg Actual Intensity` | Excludes 6 periods; shifted the figure by 0.14 gCO₂/kWh |
| `Missing Actuals %` KPI | Reported 0.14% |
| Dashboard Data Quality page | Showed the warning, as intended |
| Historical analysis | Not affected — all six are in the final three hours |

Handling at the time: nulls were **left empty, not estimated**. Imputing a value
would have put a fabricated number into a forecast-accuracy metric, which is the
one metric where a fabricated actual does the most damage.

## Resolution

**Fixed.** `extract.py` gained a `backfill_hours` parameter, default 48, surfaced as
`--backfill-hours`. Any cached chunk overlapping the last N hours of the window is
re-fetched rather than replayed from disk. The existing upsert then corrects the
rows in place.

Verified end to end on 7 November 2026:

```
chunk intensity_20261031T0000_20261106T0000.json is inside the 48h backfill window,
  re-fetching to pick up actuals settled since the last run
extract complete: 7 chunks, 1 API requests (1 backfilled), 6 cache hits, 0 retries
load complete: 4320 fact rows written (0 new, 4320 refreshed), 4320 total
[PASS] missing_actuals: every period has a settled actual
SUCCESS | 90 days, 4320 periods | 9 checks: 9 passed, 0 failed, 0 warning(s)
```

Before and after:

| | Before | After |
|---|---|---|
| Periods with no actual | 6 | **0** |
| Total rows | 4,320 | 4,320 (unchanged — updated, not appended) |
| API requests | 0 (all cached) | 1 (only the backfilled chunk) |
| Validation warnings | 2 | 0 |

The six values that arrived:

```
2026-11-05T21:00Z  forecast 205  actual 212
2026-11-05T21:30Z  forecast 208  actual 214
2026-11-05T22:00Z  forecast 213  actual 213
2026-11-05T22:30Z  forecast 213  actual 220
2026-11-05T23:00Z  forecast 215  actual 222
2026-11-05T23:30Z  forecast 220  actual 223
```
